The user has no Claude.ai account and only a third-party relay (中转站) key for https://www.micuapi.ai. Claude Code CLI is configured through ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN user env vars.

Claude Desktop is used in third-party ("3P") gateway mode, NOT via claude.ai login. Its config lives in `%LOCALAPPDATA%\Claude-3p\` (claude_desktop_config.json with `deploymentMode: 3p`, plus `configLibrary\_meta.json` and per-entry JSON holding inferenceProvider=gateway, inferenceGatewayBaseUrl, inferenceGatewayApiKey). The normal `%APPDATA%\Claude\` config is irrelevant for 3P.

Two desktop installs exist on this Windows PC as of 2026-09-11: an MSIX package (Claude_pzs8sxrjxfjjc in WindowsApps, SignatureKind=Developer, i.e. NOT from the Microsoft Store; it was installed by the official "Claude Setup.exe" downloaded from downloads.claude.ai at 09:12 on 2026-09-11; launch via `explorer.exe shell:AppsFolder\Claude_pzs8sxrjxfjjc!Claude`) and a legacy Squirrel install (`%LOCALAPPDATA%\AnthropicClaude`; installed 09:19 by double-clicking, then re-installed 09:28 with `--silent` by the colleague-provided script `install-sub2api-codex-claude-windows.ps1`, both from the offline installer `Claude-Desktop-1.13576.4-win32-x64.exe` that sits next to the script in `WPSDrive\...\朗坤\work\工具\win11和Linux安装配置Claude code和Codex自动化脚本\` — that folder came from a 205 MB WeChat zip received 2026-07-24; the exe is genuinely Anthropic-signed, just old. Squirrel then auto-updated from api.anthropic.com to 1.52386.0 at 10:12. The Start-menu shortcuts point to this Squirrel build). The gateway itself works in the Squirrel build (log: "3P mode active", "Model discovery: 11 found", "ConfigHealth healthy"), BUT in app 1.52386.0 the Squirrel build cannot run Code or Cowork sessions on Windows: the yukonSilver/VM gate returns `msix_required` (toast "Reinstall the desktop app to access Cowork...") and the chat composer blocks every send ("cowork submit blocked (preflight failed)"). The MSIX build ships `cowork-svc.exe` and its AppxManifest excludes `%LOCALAPPDATA%\Claude-3p` from virtualization, so it reuses the same 3P config. Hyper-V/HCS services (vmcompute, HvHost, vmms, hns) are running on the PC.

Proxy gotcha (found 2026-09-11 afternoon): the desktop app logs "[CCD] Resolved system proxy for Code sessions: http://127.0.0.1:33210" and passes it to the CLI as HTTP_PROXY/HTTPS_PROXY, taken from the WinINET registry `ProxyServer` value even when `ProxyEnable=0`. The user runs a local proxy client on 127.0.0.1:33210; when it is closed, every desktop chat fails with "API Error: Connection refused (ConnectionRefused)" and the UI shows "Request failed. Retrying in Ns (attempt N of 10)". The Electron main process itself goes direct (Chromium honors ProxyEnable) so title-gen still reaches the gateway. Standalone `claude` CLI is unaffected because no proxy env var is set. micuapi.ai is reachable without the proxy. The relay also fingerprints clients: raw curl gets HTTP 400 "检测到您的客户端存在异常... use the standard Claude Code client" and, with the Claude Code system prompt only, HTTP 503 "this group only allows Claude Code clients". Both CLI builds (standalone 2.1.268 and the desktop-bundled 2.1.266 under Claude-3p\claude-code) pass that check.

"Can't reach www.micuapi.ai" banner (diagnosed 2026-09-17): the desktop keeps a ConfigHealth state (`main.log`: "[custom-3p] ConfigHealth recomputed { state: 'unreachable' ... }") set when its gateway probe (GET /v1/models discovery) fails — e.g. `net::ERR_PROXY_CONNECTION_FAILED` when ProxyEnable=1 points at 127.0.0.1:33210 but the proxy client is off at probe time. The state LATCHES: no automatic re-probe flips it back, so the banner stays for hours even after the network recovers ("Check again" or a successful recheck clears it; network was fully working while the banner still showed). Unauthenticated /v1/models returns 401; title-gen probes get HTTP 400 "Gateway rejected model" for haiku/fable ids — those don't drive the banner. Fix applied 2026-09-17: set WinINET `ProxyOverride` (was empty) to `www.micuapi.ai;*.micuapi.ai` so gateway traffic goes direct regardless of the proxy client (verified: micuapi resolves direct, baidu still via 127.0.0.1:33210). Caveat: a Clash-type client that manages the system proxy may overwrite ProxyOverride — if the banner recurs, re-add the bypass in the proxy client's own settings.

**Why:** Earlier in that session I wrongly told the user the desktop app cannot use an API key; the 3P mode disproves that. Also the user edits JSON with PowerShell/Notepad, which adds a UTF-8 BOM that breaks the desktop app's JSON parser ("Couldn't load app settings... Unexpected token").

**How to apply:** For desktop-app issues, look in `Claude-3p\logs\main.log` first and check config files for a BOM (EF BB BF). Write JSON with `[IO.File]::WriteAllText(path, text, UTF8Encoding($false))`. Don't suggest claude.ai login flows. See [[cli-relay-config]] if written later.
